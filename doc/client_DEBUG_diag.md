## client DEBUG diag 逐字段解释

### 网络层

| 字段       | 实测值                   | 含义                                                         |
| :--------- | :----------------------- | :----------------------------------------------------------- |
| **RTT**    | 5.5~13.8ms               | HELLO→HELLO_ACK 往返时延，EWMA 平滑 |
| **jitter** | 4.44~4.60ms              | 端到端到达间隔抖动。反映网络抖动 + 发送端调度抖动，不是纯链路指标 |
| **dup**    | 0                        | 重复包数。0 说明没有重复，很好                               |
| **loss**   | 3140→3162，0.548%→0.544% | `lost + late` 的累计值，loss_rate = (lost+late)/received。注意是**会话累计**，不是瞬时 |

### 丢包拆分（关键）

| 字段          | 实测值    | 含义                                                         |
| :------------ | :-------- | :----------------------------------------------------------- |
| **late**      | 1028→1039 | 超过播放 deadline 才到达、被丢弃的包 |
| 隐含 **lost** | 2112→2123 | 到 deadline 仍未到达的包，播静音 |

所以 3140 个"损失"里，约 1/3（1028）是 late，2/3（2112）是真丢包。二者在 ~20s 内各增长约 11 个，即约 0.55 包/s —— 对局域网来说 **偏高但不致命**。

### JitterBuffer 与 RingBuffer 水位

| 字段                    | 实测值       | 含义                                                         |
| :---------------------- | :----------- | :----------------------------------------------------------- |
| **JB[cur/avg/min/max]** | 54/51/0/75ms | JitterBuffer 当前/平均/最小/最大水位 |
| **RB[cur/avg/min/max]** | 33/27/9/42ms | 播放 RingBuffer 水位，max=42ms ≈ 16KB 容量上限               |

关于 JB 水位：配置目标是 **30ms**（10 包 × 3ms，`max_catchup_ms=30`），但实测稳态约 **51ms**。这不完全是配置失效，而是 Windows 定时器粒度（~15.6ms）导致的批量 pop 设计造成的：JB 会预先缓冲约一个定时器周期 + 抖动量的 future 包，所以稳态水位 ≈ 目标30ms + 定时器~15ms + 抖动~5ms ≈ 50ms。**RB 平均 27ms 匹配 WASAPI 每 10ms 回调的平滑供数**，fill ratio 100% 也印证播放基本不缺数据。

### 调度与漂移

| 字段         | 实测值                    | 含义                                                         |
| :----------- | :------------------------ | :----------------------------------------------------------- |
| **dmiss**    | 454065→461843（~1300/5s） | deadline miss 计数：定时器比 deadline 延迟超过 1 个包（3ms）的次数 |
| **underrun** | 881→891                   | WASAPI 读不及时的次数（播静音）                              |
| **slope_s**  | -151~+114（剧烈抖动）     | RB 5s 窗口占用斜率（samples/s），反映网络抖动/调度短期波动   |
| **slope_l**  | -1.5~+5.2（接近 0）       | RB 60s 窗口占用斜率，反映真实 clock drift                    |

**dmiss 极高（45万）是预期行为**，不是故障：定时器每 ~15.6ms 才触发一次，每次批量 pop 跨越多个 3ms deadline，几乎每次都会超过 1 个包的延迟，所以自然累加。它衡量的是"定时器不精确度"，由批量 pop 机制兜底。

**slope_l 是最有价值的指标**：实测贴近 0（早期 +5，后漂向 0/-1.5），说明 server 采样速率与 client 播放速率**基本一致**，clock drift 极小（+5 samples/s @48kHz ≈ 104ppm，且会翻转，可忽略）。
