# Client DEBUG diag 逐字段解释

`--log-level debug` 下，client 每 5s 打印一行诊断日志，用于定位网络抖动、丢包、缓冲、时钟漂移等问题。

一行示例（本机回环实测，旧版本）：

```
Client diag: RTT=0.2ms jitter=4.53ms loss=388/0.527% dup=0 late=194 dmiss=54705
JB[21/25/6/42ms] RB[19/18/0/29ms] underrun=43 slope_s=179.1 slope_l=-4.7 e2e=0.0ms drift=-199.2ppm
```

> 注意：`e2e` 与 `drift` 在旧版本里分别被算成恒定 0.0 和 ±400 来回跳，那是算法缺陷（见下文"e2e / drift"两节）。当前版本已修复，回环下 `e2e` 应显示几十 ms，`drift` 应为稳定的小值。

---

## 网络层

| 字段       | 含义                                                         |
| :--------- | :----------------------------------------------------------- |
| **RTT**    | HELLO→HELLO_ACK 往返时延（ms），EWMA 平滑。反映链路 ping 级延迟。回环 0.2ms 属正常 |
| **jitter** | 端到端到达间隔抖动（ms），RFC3550 EWMA。包含网络抖动 + 发送端调度抖动，不是纯链路指标 |
| **dup**    | 重复包数（JB 归类为 duplicate）。0 说明没有重复               |
| **loss**   | `loss=N/p%`：N = `lost + late` 的**会话累计值**；p = `(lost+late)/received` 的丢包率。是累计量，不是瞬时 |

## 丢包拆分

| 字段          | 含义                                                         |
| :------------ | :----------------------------------------------------------- |
| **late**      | 超过播放 deadline 才到达、被丢弃的包（无序/抖动迟到）        |
| 隐含 **lost** | 到 deadline 仍未到达的包，播放端补静音（真丢包）             |

`loss` 的 N 是两者之和。若 `late` 占比高而 `lost` 低，多为网络抖动/乱序；若 `lost` 高，多为真丢包或拥塞。

## JitterBuffer 与 RingBuffer 水位

| 字段                    | 含义                                                         |
| :---------------------- | :----------------------------------------------------------- |
| **JB[cur/avg/min/max]** | JitterBuffer 当前/平均/最小/最大水位（ms）。稳态水位 ≈ 配置目标 + 定时器批量 pop 的预缓冲量 |
| **RB[cur/avg/min/max]** | 播放 RingBuffer 水位（ms）。容量上限 = PLAYBACK_RINGBUFFER_SIZE（16KB ≈ 42.7ms） |

JB 水位高于配置目标属正常：Windows 定时器粒度（~15.6ms）下 JB 会批量 pop，需预先缓冲约一个定时器周期 + 抖动量的 future 包。RB 水位配合 WASAPI 每 ~10ms 回调供数，`fill ratio 100%` 说明播放不缺数据。

## 调度与漂移

| 字段         | 含义                                                         |
| :----------- | :----------------------------------------------------------- |
| **dmiss**    | deadline miss 计数：定时器比 deadline 延迟超过 1 个包（AUDIO_PACKET_MS=3ms）的次数 |
| **underrun** | WASAPI 回读不及时的次数（读少于请求量，补静音）              |
| **slope_s**  | RB 5s 窗口占用斜率（samples/s），反映短期调度/网络抖动波动   |
| **slope_l**  | RB 60s 窗口占用斜率（samples/s），反映缓冲量的缓慢增减趋势   |

**dmiss 极高是预期行为**，不是故障：定时器每 ~15.6ms 才触发一次，每次批量 pop 跨越多个 3ms deadline，几乎每次都超 1 个包，故自然累加。它衡量的是"定时器不精确度"，由批量 pop 机制兜底。

## e2e（端到端延迟）

`e2e = JB 当前水位 + RB 当前水位`（ms），即**当前缓冲量**意义上的延迟。

- 无需时间同步，语义直白：此刻收到的音频还要经过多少缓冲才被播放。
- 回环下 ≈ JB(~20ms) + RB(~20ms) ≈ 40ms 量级。
- 早期版本曾用 `server 采样位置 − 本地播放位置` 计算，因 server 的 `sample_position` 是绝对源时间线（client 连接前已推进的偏移会被算进去）且无时间同步，结果恒为 0.0 或失真，已废弃。

## drift（时钟漂移）

`drift = server 发送速率 / 客户端播放速率 − 1`（ppm）。

- **server 发送速率**：对最近 10s 收到的 `(到达时间, sample_position)` 做线性回归，斜率即稳定发送速率（帧/秒）。
- **客户端播放速率**：对采集到的 `(时间, 累计播放帧数)` 做同样回归。
- 两者都用长窗口回归平均掉逐包抖动和包边界相位，得到**单一符号的稳定值**。
- 正 = server 快于播放（JB 渐满，可能溢出）；负 = server 慢于播放（JB 渐空，可能欠载）。回环下应接近 0（±几百 ppm）。

早期版本用 5s 窗口端点差分 `Δserver/Δplayed`，因采样瞬间的包边界相位噪声过大而 ±400 来回翻，已废弃。
